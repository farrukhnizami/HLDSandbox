*Royal Mail [Enter Solution/Application Acronym here, e.g PDA] - Processing Sites: Worked Example*

*The [Enter Solution/Application Acronym here, e.g PDA] Processing Sites architecture is governed by five fundamental decisions:*

=== Reuse, do not re-platform

[Enter Solution/Application Acronym here, e.g PDA] is extended, not rebuilt. Processing capabilities are added as additional bounded contexts within the existing [Enter Solution/Application Acronym here, e.g PDA] solution, sharing identity, audit, integration, master data and storage layers. This delivers cost containment and consistency across Delivery and Processing Units.

=== Data-driven planning

Duty masters (codes, work-area splits, rotation patterns) are owned by MDS and pulled into [Enter Solution/Application Acronym here, e.g PDA] on a monthly bulk cadence with on-demand deltas. [Enter Solution/Application Acronym here, e.g PDA] authoritatively derives plans from this master data; any operational variance is captured as a tracked, auditable adjustment rather than a redefinition of the duty. Additionally, [Enter Solution/Application Acronym here, e.g PDA] allows ad hoc overtime planning.

=== Plan vs. scan reconciliation as the canonical pay-validation pattern

Pay-affecting decisions (OT and Schedule-Attendance approval) cross-reference the approved plan against PDA and Console scan events. The plan is the authoritative reference for downstream timesheet validation; manual override is permitted but always logged.

=== Event-driven, API-led integration

High-volume, low-latency flows (scan events and PSP OT flow) use the IBM MQ. Lower-volume flows (Joined up and People app) use synchronous APIs through the BIG API gateway. Bulk analytics flows to the Data Platform use the Batch data export. No point-to-point integration is introduced.
